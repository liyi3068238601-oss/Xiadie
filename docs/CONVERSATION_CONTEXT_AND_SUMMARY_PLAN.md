# 遐蝶对话上下文、会话摘要与跨会话回忆施工计划

> 文档状态：施工前计划，尚未开始实现  
> 适用范围：不限总长度的对话档案、最高 1M tokens 动态上下文窗口、会话滚动摘要、跨会话历史回忆及其聊天接入
> 不包含：SecretStore 迁移、ToolRegistry、MCP、多 Agent、外部平台和桌面自动化  
> 冻结边界：现有 Fragment、Episode、Saga、记忆观察器、Archivist 和长期记忆 UI 本轮不修改
> 执行方式：每完成一个阶段，先完成测试、勾选、文档更新和独立审查，再进入下一阶段

---

## 1. 先回答产品归类问题

上下文与摘要确实属于“记忆体系”，但不应全部归入短期记忆或长期记忆。最终产品应明确分成以下五层。

| 层级 | 保存什么 | 生命周期 | 是否可丢失重建 | 当前例子 |
|---|---|---|---|---|
| 原始对话档案 | 用户与遐蝶的原始消息 | 用户删除前长期保存 | 否，原文是真实来源 | “12×8 等于多少？”及当时回复 |
| 工作记忆 / 当前上下文 | 本轮真正发送给模型的内容包 | 一次模型请求 | 是 | 系统规则、最近对话、当前问题 |
| 会话记忆 / 滚动摘要 | 较早对话的压缩结果 | 随会话持续更新 | 是，必须能从原文重建 | “双方此前讨论了窗口方案，尚待确认设置页结构” |
| 历史对话召回 | 按当前问题检索出的过去原文片段 | 一次模型请求 | 是 | 用户问“我以前问过什么算术题”时召回原消息 |
| 长期记忆 | 稳定事实、偏好、经历和长期叙事 | 跨会话长期存在 | 派生内容可重建，用户修订需保留 | Fragment、Episode、Saga |

因此，本计划的准确定位是：

> 建立“当前工作上下文 + 当前会话滚动摘要 + 跨会话历史回忆”的编排层，并通过现有只读接口消费长期记忆摘要。

会话摘要不是 Fragment，也不是 Episode 或 Saga：

- Fragment 用于保存稳定事实、偏好、计划等长期有效信息。
- Episode 用于表达一段有意义的共同经历。
- Saga 用于表达跨较长时间的连续发展。
- 会话摘要只为保持当前会话连续性和节省 token，可随时重建，不是事实权威。
- 原始消息永远比摘要更权威；两者冲突时必须以原文和用户最新纠正为准。

“12×8”这类普通问题不应进入长期 Fragment，但原始问答仍保存在对话档案中。即使用户新建另一个话题会话，遐蝶在相关问题出现时仍应能从跨会话历史中找到这次真实问答。

### 1.1 本轮与长期记忆的唯一交界

本轮只允许一条只读交界：

```text
现有 memory.build_digest(...) 或其等价稳定接口
                    ↓
           ContextAssembler 分配预算
                    ↓
              发送给聊天模型
```

允许做的事：

- 统计现有记忆摘要占用了多少上下文预算。
- 当总预算不足时，要求现有记忆接口按既有规则返回更小的摘要，或把该需求记录为后续兼容接口。
- 在无正文诊断元数据中记录本轮是否使用了既有记忆及其数量。

禁止做的事：

- 修改 `memory_fragments`、`memory_episodes`、`memory_sagas` schema。
- 修改自动记忆观察、候选生成、Episode/Saga 整理、Archivist 生命周期或召回排序。
- 新增 Episode/Saga 到普通聊天的注入链路。
- 为了摘要方便而重新解释、复制或迁移长期记忆数据。
- 让会话摘要自动创建、纠正、覆盖或删除长期记忆。

如果现有长期记忆摘要超过可分配预算，本轮只能在 ContextAssembler 边界进行保守处理，不得进入长期记忆内部重构。

### 1.2 产品体验目标：像 ChatGPT，而不是像记忆数据库后台

本计划最终以 ChatGPT 式的可观察体验为目标，但不猜测或复制其未公开的内部实现：

1. **同一聊天自然连续。** 用户不需要手动管理 token 或摘要；聊天很长时，系统在后台压缩较早内容，并保留最近原文。
2. **旧内容由摘要承接。** 用户无需手动决定何时压缩，也不会看到原消息被摘要覆盖或删除。
3. **现有长期记忆继续照常工作。** 本轮不改变“记住/忘掉”、Fragment、Episode 或 Saga 行为。
4. **多个会话共享连续经历。** 新建会话只是为了整理不同话题，不代表遐蝶失去其他会话中的经历。
5. **按需回忆过去原文。** 当前问题与旧聊天相关时，系统检索少量真实片段，而不是把全部历史发送给模型。
6. **回忆融入自然对话。** 普通聊天不显示“已参考记忆”“已参考过往聊天”等检索提示，也不把陪伴体验做成知识库问答；摘要版本、token 分配和来源定位只用于受限的内部诊断。

对应到遐蝶内部：

```text
ChatGPT 式“当前聊天连续性”  → ContextAssembler + 最近原文 + 会话滚动摘要
现有“已保存记忆”能力        → 原样保留，通过既有只读摘要接口接入
“参考聊天历史”能力          → 本地跨会话历史检索 + 原消息证据
```

这意味着 Episode、Saga、摘要任务和 token 预算仍可保留为强大的内部能力，但不应成为普通用户每次聊天前必须理解或操作的概念。

### 1.3 用户能够理解的状态

普通聊天界面只需表达以下状态：

普通用户不需要区分 Fragment、会话摘要、历史召回或当前上下文。遐蝶应像长期相处的伴侣一样自然延续谈话；仅当用户主动询问“你为什么记得”“我们什么时候聊过”时，才用自然语言说明大致来源，必要时帮助用户定位原会话。

默认不显示“用了 832 个摘要 token”“summary revision 7”“已检索 3 段历史”等工程信息；这些内容只进入受限的开发者诊断，并且不得破坏聊天界面的陪伴感。

## 3. 目标与非目标

### 3.1 核心目标

1. 任意模型请求都能在发送前证明不超过该模型的输入上下文预算。
2. 不限制会话保存总长度，不设置固定轮数；用户可以长期持续聊天。
3. 产品级单次上下文上限定为 1,000,000 tokens，并受当前模型真实能力约束。
4. 单次模型请求动态使用有效安全窗口，不会静默丢失早期语境。
5. 最近对话保留原文，较早对话由滚动摘要承接。
6. 当前问题需要过去经历时，可从其他会话检索真实原文，而不是让模型凭摘要猜测。
7. 现有长期记忆、知识库、会话摘要与跨会话历史保持清晰边界。
8. 摘要永远不覆盖、不删除、不修改原始消息。
9. 用户能够看见摘要是否启用、覆盖到哪里、是否失败，并可关闭或重建。
10. 整套机制支持模型切换、重新生成、会话删除、应用重启与数据库升级。
11. 普通用户不需要理解上下文窗口、token 或滚动摘要也能自然使用。

### 3.2 非目标

- 不实现临时聊天；该能力需要同时约束记忆观察、历史与数据保留，应另立专项。
- 不把每条普通对话自动写入长期记忆。
- 不自动把会话摘要提升为 Fragment、Episode 或 Saga。
- 不删除旧消息来节省数据库空间。
- 不在日志或审计事件中复制消息正文、摘要正文或模型原始输出。
- 不承诺从任意长度历史中逐字复现所有内容；精确回忆必须依赖可检索的原消息。
- 不因本计划重写现有记忆、知识或聊天模块。
- 不修改现有长期记忆设置、UI、召回策略、后台 worker 或数据库表。
- 不复刻 ChatGPT 的界面、品牌或未公开内部机制，只实现相近的用户能力边界。

## 4. 必须冻结的设计原则

### 4.1 原文是唯一事实来源

1. `messages` 保存原始聊天记录。
2. 摘要只保存对原文的派生表达和来源边界。
3. 摘要必须记录覆盖的首尾消息 ID、消息数量、来源哈希和协议版本。
4. 用户修改、删除或重新生成被摘要覆盖的消息时，相关摘要必须失效或重建。
5. 回答“我原来具体说了什么”时，应优先引用原文，不得只依赖摘要复述。

### 4.2 当前问题不可被裁掉

当前用户消息、安全规则、核心人格边界和必要协议字段属于受保护区。如果这些内容加输出预留已经超过模型窗口，系统必须在调用 Provider 前返回可理解错误，不能继续发送，也不能静默截断当前问题。

### 4.2.1 1M 上下文上限与不限历史的准确含义

本产品不设置以下人为限制：

- 不限制一个会话最多保存多少轮。
- 不因会话过长删除原始消息。
- 不用固定的 20 轮、100 轮或某个累计 token 数强制用户新建会话。
- 不给全部本地对话档案设置一个与模型窗口相同的容量上限。

产品级单次上下文上限定为：

```text
APPLICATION_CONTEXT_CEILING_TOKENS = 1_000_000
```

实际有效窗口必须这样计算：

```text
effective_context_window = min(
    1_000_000,
    verified_model_context_window,
)
```

其中：

- 模型经验证支持 1M 或更大窗口时，遐蝶最多使用 1M。
- 模型只支持 128K、64K 或更小窗口时，必须使用模型真实窗口，不能伪报 1M。
- 未知模型不得默认假定支持 1M，应使用保守值或要求用户确认配置。
- 1M 是可用上限，不是每轮必须填满的目标；系统只注入当前回答真正需要的内容。
- 输出 token、消息封装和安全余量仍从有效窗口中预留。

动态处理关系为：

```text
不限长度的本地对话档案
          ↓ 检索与压缩
当前会话摘要 + 最近原文 + 跨会话相关片段 + 现有记忆 digest
          ↓
当前模型可接受的一次请求
```

因此，产品层面“没有会话长度上限”，应用层面“单次最多 1M”，模型层面“不得超过模型真实窗口”。三者不能混为一谈。

### 4.3 硬预算高于“至少保留几轮”

“尽量保留最近 4 轮”只能是软目标，不得突破模型窗口。任何组件加入后都必须重新验证总预算不变量。

### 4.4 摘要不是长期事实

摘要允许压缩：讨论主题、已有决定、未决问题、用户纠正、当前任务状态和必要指代关系。它不得因为一句含糊表达而创造稳定用户偏好，也不得自动修改长期记忆。

### 4.5 明确远程摘要的数据去向

如果摘要由模型生成，必须明确摘要模型及数据去向。当前策略默认允许摘要模型处理生成摘要所需的历史对话；用户切换到新的远程 Provider 后，设置页必须透明展示解析后的 Provider、模型和远程执行位置。

第一版采用以下规则：

- 没有可用的摘要模型时，聊天仍可通过安全裁剪运行，摘要状态显示为“未生成”。
- 摘要模型可以跟随当前模型或由用户单独配置。
- 从本地模型切到远程模型、或从一个远程服务切到另一个服务时，任务仍绑定数据位置 revision，陈旧任务不得跨位置继续执行。
- 后台摘要调用不得阻塞当前聊天回复。

### 4.6 长期记忆冻结规则

- `ContextAssembler` 只能消费现有长期记忆模块已经返回的 digest 与引用元数据。
- 本计划不得直接查询 Fragment、Episode 或 Saga 来建立新的召回路径。
- 本计划不得改变“记忆已关闭”时的现有行为。
- 会话摘要与长期记忆冲突时，摘要不得反向修正长期记忆；本轮只标记摘要失效并从当前会话原文重建。
- 长期记忆接口若暂时不能接受预算参数，先按现有输出接入；是否增加只读的 `max_tokens` 参数必须作为独立兼容 PR，且不改变召回结果语义。

## 5. 统一上下文包

每次聊天不再由 `main.py` 临时拼接数组，而是由 `ContextAssembler` 产生一个结构化结果：

```text
ContextPackage
├─ policy_and_persona       必保留
├─ current_user_message     必保留
├─ recent_raw_turns         尽量保留完整轮次
├─ rolling_summary          较早会话压缩
├─ cross_session_recall     其他会话中的少量相关原文/摘要
├─ existing_memory_digest   现有长期记忆接口的只读结果
├─ lore                     角色设定
├─ knowledge                用户知识库证据
└─ budget_report            仅元数据，不发送给模型
```

### 5.1 总预算不变量

发送前必须满足：

```text
系统规则与人格
+ 当前用户输入
+ 最近原始对话
+ 会话摘要
+ 跨会话相关历史
+ 现有长期记忆摘要
+ Lore
+ 知识库
+ 消息封装与安全余量
+ 预留输出 token
<= 当前 Provider + Model 的上下文窗口
```

若不满足，则按以下顺序缩减：

1. 减少低相关知识片段。
2. 减少低相关跨会话历史片段。
3. 使用现有长期记忆模块已经提供的压缩结果；若可选 digest 仍无法容纳，则不注入并在 meta 中说明，不能进入长期记忆内部改召回规则。
4. 减少更早的最近原文轮次，并由摘要承接。
5. 压缩 Lore 的非核心部分。
6. 若受保护区仍无法放入，调用前失败并提示用户缩短输入或切换更大上下文模型。

不得通过裁剪当前用户消息、安全规则或输出预留来“凑够”预算。

### 5.2 模型能力来源

模型窗口必须按 `provider_id + model_id` 解析，优先级为：

1. 已验证的 ModelProfile 能力值。
2. Provider 能力发现或官方适配器的模型映射。
3. 用户显式配置的保守值。
4. 未知模型使用保守默认值并标记 `unverified`。

不再在 `context_budget.py` 中维护一份仅按 Provider 名称判断的长期硬编码表。

无论能力来源如何，最终 `effective_context_window` 均不得超过 1,000,000 tokens。

### 5.3 token 估算策略

- 第一版允许使用本地保守估算，但只能有一个权威实现。
- 估算接口必须能区分消息正文、角色封装、工具协议和附件描述。
- 可用时由适配器提供更精确 tokenizer；不可用时使用保守系数并增加 safety margin。
- 每次请求都记录估算版本、总量和各组件数量，不记录正文。
- Provider 返回真实 usage 时，记录估算误差，用于离线校准，不自动放宽安全边界。

## 6. 会话滚动摘要设计

### 6.1 摘要应该保留的内容

- 当前会话的主题和目标。
- 用户已经明确作出的决定。
- 用户对旧内容的纠正。
- 已完成、正在进行和未解决的事项。
- 后文仍会引用的人物、文件、项目和术语。
- 遐蝶已经作出的承诺或需要继续履行的动作。
- 必要的情绪与关系语境，但不得把瞬时情绪固化为永久事实。

### 6.2 摘要不应保留的内容

- 可从长期记忆直接获取且与会话连续性无关的重复事实。
- 无后续意义的寒暄和一次性计算细节。
- 密码、API Key、令牌、身份证号等秘密。
- 模型内部推理。
- 没有原文支持的推断。
- 知识库正文的大段复制。

### 6.3 建议数据模型

```text
conversation_summary_revisions
├─ id
├─ session_id
├─ revision
├─ status
├─ protocol_version
├─ source_start_message_id
├─ source_end_message_id
├─ source_message_count
├─ source_sha256
├─ summary_text
├─ open_threads_json
├─ decisions_json
├─ corrections_json

```

### 6.4 版本与失效

- 同一会话任一时刻只有一个 active 摘要版本。
- 新摘要原子激活后，旧摘要变为 superseded。
- 摘要覆盖的来源范围必须连续，不能跳过中间消息。
- 重新生成替换消息后，覆盖旧 assistant message 的摘要必须失效。
- 删除会话时通过外键级联删除摘要和任务。
- 应用崩溃后可恢复 queued/running 任务，但不能重复激活相同来源哈希。
- 增量摘要允许使用“旧 active 摘要 + 新增原文”，但必须定期从原始消息全量重建以控制摘要漂移。

### 6.5 触发策略

触发不应只看“轮数”，而应同时考虑：

- 当前模型的可用输入预算。
- 未摘要历史的估算 token。
- 最近原文保护窗口。
- 上次 active 摘要覆盖位置。
- 当前是否已有同来源任务。

建议行为：

1. 低于软阈值：不生成摘要，直接保留原文。
2. 接近软阈值：后台生成或更新摘要。
3. 摘要尚未完成但用户继续聊天：安全裁剪旧原文，当前请求不中断。
4. 达到硬阈值：只使用已验证摘要和可容纳的最近完整轮次。
5. 连受保护区都无法容纳：调用前明确失败。

## 7. 跨会话历史回忆设计

### 7.1 产品原则：会话是话题分组，不是记忆边界

遐蝶是陪伴型 Agent。用户新建会话主要为了：

- 整理不同话题。
- 避免一个侧栏条目无限混杂。
- 方便查找项目、生活、闲聊等不同记录。

新建会话不代表创建一个“失忆的遐蝶”。除非用户明确永久删除数据或关闭历史回忆，所有保留的会话都属于同一个连续陪伴历史。

### 7.2 为什么摘要还不够

摘要是有损的。用户可能问：

- “我以前是不是问过你 12×8？”
- “我当时对 UI 的原话是什么？”
- “我们第一次提到 Blender 是哪次？”

这些问题必须回到原始消息或有来源的会话摘要，而不是依赖长期记忆或模型猜测。

### 7.3 检索范围与优先级

1. 当前会话最近原文。
2. 当前会话已被滚动摘要覆盖的旧原文。
3. 其他会话的标题、会话摘要和相关原始消息。
4. 现有长期记忆 digest；它仍由原系统独立提供。

跨会话召回要求：

- 使用本地可重建索引；原文权威仍在 `messages`。
- 先检索会话级标题/摘要，再在高相关会话中检索消息，避免全库粗暴拼接。
- 返回完整轮次或必要相邻上下文，避免断章取义。
- 每个片段带 session ID、message ID、时间和原对话入口。
- 相关性、明确回忆意图、时间和话题连续性共同排序；不能只按最近时间。
- 普通问题不会因为共享历史而注入大量无关旧聊天。
- 召回结果受单次请求动态窗口约束，但本地历史存储总量不受该窗口限制。

#### 7.3.1 可解释的两阶段召回评分

跨会话召回不得只依赖一个不可解释的模型分数，也不得把“越新”误当成“越相关”。第一版采用两阶段候选排序：

1. **会话级召回：** 根据会话标题、active 摘要、关键词与语义相关性选出少量候选会话。
2. **消息级召回：** 只在候选会话中检索原始消息，并扩展为完整问答轮次或必要相邻消息。

在评分前先执行硬过滤：已永久删除、被用户排除、无权访问、来源失效或不允许参与历史回忆的内容不得成为候选。

评分至少包含以下可审计信号：

- 语义相关性；
- 关键词、FTS 或 BM25 匹配；
- 用户明确的回忆意图或引用线索；
- 当前话题与候选会话的连续性；
- 时间连续性或合理的时间范围；
- 稳定的会话元数据，例如用户置顶或明确标记的重要会话。

这些信号的权重必须配置化、版本化并通过离线评测校准，例如记录为 `conversation-recall-v1`；不得在计划阶段随意冻结一组未经验证的权重。时间新近性只能作为有限加分，不能压过明确引用和语义证据。“会话重要度”只能来自稳定、可解释的元数据或经验证摘要，不能由模型临时臆测。

召回诊断只记录候选 ID、评分分量、排序版本和淘汰原因，不记录完整消息正文。最终结果还需做去重、来源多样性与完整轮次扩展，避免同一会话的相似片段占满预算。

### 7.4 与长期记忆的区别

```text
跨会话历史回忆：回答“我们具体说过什么”，证据是 messages 与会话摘要。
现有长期记忆：回答“你是谁、偏好什么、我们形成了什么长期经历”。
```

本轮不得用历史召回结果写回、纠正或删除 Fragment、Episode、Saga。两者只在 ContextAssembler 中作为不同来源共同参与本轮回答。

### 7.5 新建、归档、清空与删除语义

- **新建会话：** 只创建新的话题容器，不影响任何历史、摘要或长期记忆。
- **关闭窗口：** 不影响任何数据。
- **归档会话：** 从常用列表隐藏，但默认仍属于可回忆历史；未来可增加“归档后不参与回忆”的独立选项。
- **清空当前输入上下文：** 开始新的当前会话上下文，但不删除历史档案和长期记忆。
- **永久删除会话：** 删除该会话原文、滚动摘要和历史索引；必须明确警告未来无法逐字回忆该会话。
- **长期记忆：** 永久删除会话不自动删除现有 Fragment、Episode、Saga，因为长期记忆是独立系统；如用户要彻底清除相关信息，应走单独且明确的长期记忆删除流程。

默认应优先提供“新建会话”或“归档”，不把永久删除伪装成普通的“清空上下文”。

### 7.6 自然回忆与内部可追溯

跨会话历史被使用时，普通聊天界面不展示来源徽标、数量、评分、引用卡片或检索过程。遐蝶直接以符合当前语境的自然语言延续对话，避免让用户感到自己在操作检索系统。

内部仍必须保留 source locator、来源类型、时间和必要哈希，用于错误排查、删除传播和防止摘要冒充原话，但这些元数据默认不进入聊天流或普通用户界面。只有用户主动询问来源时，系统才生成面向人的简短说明；若需要定位原文，可提供进入原会话的操作，但不常驻展示证据面板。

回答中若复述历史，只能把直接来自 `messages` 的内容称为原话；会话摘要只能作为语义背景，不能伪装成逐字引用。无法确认原文时，应使用“我记得我们大致讨论过……”等不夸大确定性的表达。

## 9. 必测场景矩阵

| 场景 | 预期结果 |
|---|---|
| 短会话 | 不必生成摘要，保留完整最近原文 |
| 长会话，摘要可用 | 注入 active 摘要 + 摘要后的最近完整轮次 |
| 长会话，摘要失败 | 安全裁剪，聊天继续，meta 标明摘要不可用 |
| 系统提示过长 | Provider 调用前失败，不伪造可用预算 |
| 当前用户输入过长 | 明确提示缩短输入或更换模型 |
| 切换小上下文模型 | 重新编排，不沿用大模型预算 |
| 128K 模型配置 | 有效窗口为 128K，不伪装成 1M |
| 已验证 1M 模型配置 | 有效窗口为 1M，扣除输出与安全余量后组装输入 |
| 模型能力超过 1M | 应用仍以 1M 为单次上限 |
| 切换远程 Provider | 新摘要任务使用新位置绑定并展示数据去向；陈旧绑定不执行 |
| 重新生成最后回复 | 旧回复成功替换后使相关摘要失效/重建 |
| 新建另一个话题会话 | 旧会话仍可按相关性被回忆，不视为失忆 |
| 归档会话 | 从常用列表隐藏，但默认仍参与历史回忆 |
| 永久删除会话 | 原文、会话摘要和索引级联清理；现有长期记忆不受影响 |
| 当前会话再次问“我刚才问过 12×8 吗” | 从本会话最近原文或滚动摘要继续，不新建长期 Fragment |
| 新会话询问“我以前问过什么算术题” | 跨会话召回真实原消息并提供原对话入口 |
| 现有记忆开启/关闭 | 完全沿用当前长期记忆系统行为；本计划不改变 |
| 摘要与原文冲突 | 原文和用户最新纠正优先，摘要失效 |
| 知识库内容很长 | 知识先按独立预算缩减，不挤掉当前问题 |
| Provider 返回 context error | 记录结构化错误；仅在无副作用前提下允许一次保守重编排 |

## 10. 审查规则

1. 每个 CTX 阶段使用独立分支或最小 PR，不跨阶段“顺手实现”。
2. 每阶段完成后生成专属审查材料；下一阶段开始前只读取一次新审查反馈。
3. 审查报告若基于过时测试数、过时 schema 或旧源码，必须先校准基线再决定是否采纳。
4. 审查建议分为：采纳、调整后采纳、推迟、拒绝；每项写清理由和落点。
5. 未完成的测试、UI、迁移或隐私项不能因“主流程可用”而提前打勾。
6. 阶段提交不得包含用户已有的无关工作区改动。
7. 所有新增事件表都要验证不保存正文、摘要正文和模型原始输出。
8. 所有模型生成摘要都必须经过本地 Schema、来源和敏感信息校验。
9. 所有预算结论必须由测试证明，不接受“通常不会超过”的经验判断。
10. 总验收之前不得删除临时兼容接口；总验收后应清除重复 estimator、失效常量和旧拼接路径。

## 13. 最终产品体验

完成本计划后，用户应感受到：

1. 同一会话聊很久，遐蝶仍能延续早期决定和未完成话题。
2. 她不会因为上下文变长突然报错，也不会无提示忘掉前文。
3. 她记得稳定偏好，是长期记忆在工作。
4. 她对当前长会话的连续理解，是滚动摘要与最近原文共同工作。
5. 用户新建不同话题会话后，遐蝶仍能按需回忆其他会话的相关内容。
6. 用户始终可以打开原会话验证，而不必相信一段不可追溯的摘要。
7. 已经完成的长期记忆系统继续独立工作，不因本计划发生行为变化。

一句话定义：

> 长期记忆继续负责“你是谁、我们经历过什么”；会话摘要负责“当前话题谈到哪里”；跨会话历史负责“过去具体说过什么”；上下文编排器负责在不改长期记忆的前提下决定本轮该把哪些内容交给模型。
