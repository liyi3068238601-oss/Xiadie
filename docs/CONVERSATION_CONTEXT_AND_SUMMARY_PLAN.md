> 文档状态：施工前计划，尚未开始实现

## 1. 先回答产品归类问题

上下文与摘要确实属于“记忆体系”，但不应全部归入短期记忆或长期记忆。最终产品应明确分成以下五层。

| 层级 | 保存什么 | 生命周期 | 是否可丢失重建 | 当前例子 |
|---|---|---|---|---|
| 原始对话档案 | 用户与遐蝶的原始消息 | 用户删除前长期保存 | 否，原文是真实来源 | “12×8 等于多少？”及当时回复 |
| 工作记忆 / 当前上下文 | 本轮真正发送给模型的内容包 | 一次模型请求 | 是 | 系统规则、最近对话、当前问题 |
| 会话记忆 / 滚动摘要 | 较早对话的压缩结果 | 随会话持续更新 | 是，必须能从原文重建 | “双方此前讨论了窗口方案，尚待确认设置页结构” |
| 历史对话召回 | 按当前问题检索出的过去原文片段 | 一次模型请求 | 是 | 用户问“我以前问过什么算术题”时召回原消息 |
| 长期记忆 | 稳定事实、偏好、经历和长期叙事 | 跨会话长期存在 | 派生内容可重建，用户修订需保留 | Fragment、Episode、Saga |

因此，本计划的准确定位是：

> 建立“工作记忆 + 会话记忆 + 历史对话召回 + 长期记忆”的统一上下文编排层。

会话摘要不是 Fragment，也不是 Episode 或 Saga：

- Fragment 用于保存稳定事实、偏好、计划等长期有效信息。
- Episode 用于表达一段有意义的共同经历。
- Saga 用于表达跨较长时间的连续发展。
- 会话摘要只为保持当前会话连续性和节省 token，可随时重建，不是事实权威。
- 原始消息永远比摘要更权威；两者冲突时必须以原文和用户最新纠正为准。

“12×8”这类普通问题不应进入长期 Fragment，但原始问答仍保存在对话档案中；当用户明确询问过去谈过什么时，应由历史对话召回找到，而不是污染长期记忆。

### 1.1 产品体验目标：像 ChatGPT，而不是像记忆数据库后台

本计划最终以 ChatGPT 式的可观察体验为目标，但不猜测或复制其未公开的内部实现：

1. **同一聊天自然连续。** 用户不需要手动管理 token 或摘要；聊天很长时，系统在后台压缩较早内容，并保留最近原文。
2. **新聊天可参考过去。** 开启“参考聊天历史”后，遐蝶按需找回相关旧对话，而不是把全部历史塞给模型。
3. **明确记忆独立存在。** 用户说“记住……”时写入可管理的长期记忆；说“忘掉……”时可以删除或禁用对应记忆。
4. **聊天历史长期可查。** 未进入长期记忆的普通问答仍能通过历史搜索和原对话入口找回。
5. **提供临时聊天。** 临时聊天不读取个人长期记忆、不参考其他聊天、不产生新的长期记忆，并按单独的数据保留策略处理。
6. **默认界面保持简单。** 普通用户只看到“已参考记忆”“已参考过往聊天”等轻提示；摘要版本、token 分配和来源哈希只放在高级诊断中。

对应到遐蝶内部：

```text
ChatGPT 式“当前聊天连续性”  → ContextAssembler + 最近原文 + 会话滚动摘要
ChatGPT 式“参考聊天历史”    → 本地历史对话召回
ChatGPT 式“已保存记忆”      → Fragment（必要时由 Episode/Saga 提供经历背景）
ChatGPT 式“搜索聊天”        → sessions/messages 本地搜索与原对话入口
ChatGPT 式“临时聊天”        → 独立的 ephemeral session 策略
```

这意味着 Episode、Saga、摘要任务和 token 预算仍可保留为强大的内部能力，但不应成为普通用户每次聊天前必须理解或操作的概念。

### 1.2 用户能够理解的四种状态

普通聊天界面只需表达以下状态：

| 用户看到的状态 | 实际含义 |
|---|---|
| 已参考记忆 | 使用了经过筛选的长期记忆 |
| 已参考过往聊天 | 使用了其他会话或当前会话较早原文 |
| 当前聊天已自动整理 | 较早内容已由滚动摘要承接 |
| 临时聊天 | 不读取或写入个人记忆，不跨会话引用 |

默认不显示“用了 832 个摘要 token”“summary revision 7”等工程信息；这些内容只在开发者诊断或用户主动展开详情时出现。

## 3. 目标与非目标

### 3.1 核心目标

1. 任意模型请求都能在发送前证明不超过该模型的输入上下文预算。
2. 长会话不再无限携带全部原文，也不会静默丢失早期语境。
3. 最近对话保留原文，较早对话由滚动摘要承接。
4. 用户需要精确回忆时，可以检索过去的真实消息，而不是让模型凭摘要猜测。
5. Fragment、Episode、Saga、知识库与聊天摘要各自保持清晰边界。
6. 摘要永远不覆盖、不删除、不修改原始消息。
7. 用户能够看见摘要是否启用、覆盖到哪里、是否失败，并可关闭或重建。
8. 整套机制支持模型切换、重新生成、会话删除、应用重启与数据库升级。
9. 普通用户不需要理解上下文窗口、token、Fragment、Episode 或 Saga 也能自然使用。
10. 形成“已保存记忆”和“参考聊天历史”两个相互独立的用户开关。
11. 支持类似 ChatGPT 的临时聊天，不把临时内容带入未来对话。

### 3.2 非目标

- 不在本阶段实现完整语义向量历史搜索；第一版可使用 SQLite FTS 与确定性排序。
- 不把每条普通对话自动写入长期记忆。
- 不自动把会话摘要提升为 Fragment、Episode 或 Saga。
- 不删除旧消息来节省数据库空间。
- 不在日志或审计事件中复制消息正文、摘要正文或模型原始输出。
- 不承诺从任意长度历史中逐字复现所有内容；精确回忆必须依赖可检索的原消息。
- 不因本计划重写现有记忆、知识或聊天模块。
- 不复刻 ChatGPT 的界面、品牌或未公开内部机制，只实现相近的用户能力边界。

## 4. 必须冻结的设计原则

### 4.1 原文是唯一事实来源

1. `messages` 保存原始聊天记录。
2. 摘要只保存对原文的派生表达和来源边界。
3. 摘要必须记录覆盖的首尾消息 ID、消息数量、来源哈希和协议版本。
4. 用户修改、删除或重新生成被摘要覆盖的消息时，相关摘要必须失效或重建。
5. 回答“我原来具体说了什么”时，应优先引用原文，不得只依赖摘要复述。

### 4.2 当前问题不可被裁掉

当前用户消息、安全规则、核心人格边界和必要协议字段属于受保护区。如果这些内容加输出预留已经超过模型窗口，系统必须在调用 Provider 前返回可理解错误，不能继续发送，也不能静默截断当前问题。

### 4.3 硬预算高于“至少保留几轮”

“尽量保留最近 4 轮”只能是软目标，不得突破模型窗口。任何组件加入后都必须重新验证总预算不变量。

### 4.4 摘要不是长期事实

摘要允许压缩：讨论主题、已有决定、未决问题、用户纠正、当前任务状态和必要指代关系。它不得因为一句含糊表达而创造稳定用户偏好，也不得自动修改长期记忆。

### 4.5 不让不同远程 Provider 意外看到旧历史

如果摘要由模型生成，必须明确摘要模型及数据去向。用户切换到新的远程 Provider 时，不得在没有明确策略的情况下把大量旧消息发送给该 Provider 做摘要。

第一版采用以下规则：

- 没有可用或获准的摘要模型时，聊天仍可通过安全裁剪运行，摘要状态显示为“未生成”。
- 摘要模型可以跟随当前模型或由用户单独配置。
- 从本地模型切到远程模型、或从一个远程服务切到另一个服务时，旧消息摘要需要遵守数据位置策略。
- 后台摘要调用不得阻塞当前聊天回复。

### 4.6 已保存记忆与聊天历史彼此独立

为了形成 ChatGPT 式体验，必须固定以下语义：

- 关闭“已保存记忆”后，不向聊天注入 Fragment、Episode 或 Saga，也不新增自动长期记忆。
- 关闭“参考聊天历史”后，不检索其他会话；当前会话最近原文和内部滚动摘要仍可用于维持本次聊天连续性。
- 删除或归档一个聊天后，该聊天不再参与跨会话历史召回。
- 已经从该聊天产生的正式长期记忆不会被静默一起删除，因为两者是独立数据；删除聊天时必须明确提示这一点。
- 产品应提供“同时清除本聊天及其派生长期记忆”的显式高级操作，并展示影响范围。
- 删除长期记忆不删除原聊天；用户仍可在历史中找到当时的原话，除非同时删除聊天。

### 4.7 临时聊天语义

临时聊天保留遐蝶的人格和安全规则，但：

- 不读取 Fragment、Episode、Saga 或其他会话历史。
- 不触发记忆观察器、Episode/Saga 整理或跨会话索引写入。
- 当前临时聊天内部仍可使用短期上下文和仅在该临时会话内存在的滚动摘要。
- 不默认出现在普通聊天历史列表。
- 必须定义明确的进程内或短期本地保留、崩溃恢复与到期清理策略；不能只在 UI 上标记“临时”。
- 用户显式上传的知识文件是否允许在临时聊天使用，必须逐次选择，不沿用过去授权。

## 5. 统一上下文包

每次聊天不再由 `main.py` 临时拼接数组，而是由 `ContextAssembler` 产生一个结构化结果：

```text
ContextPackage
├─ policy_and_persona       必保留
├─ current_user_message     必保留
├─ recent_raw_turns         尽量保留完整轮次
├─ rolling_summary          较早会话压缩
├─ historical_recall        按需召回的过去原文
├─ memory_fragments         稳定长期事实
├─ memory_episodes          相关经历
├─ memory_sagas             相关长期叙事
├─ lore                     角色设定
├─ knowledge                用户知识库证据
└─ budget_report            仅元数据，不发送给模型
```

### 5.1 总预算不变量

发送前必须满足：

```text
系统规则与人格
+ 当前用户输入
+ 最近原始对话
+ 会话摘要
+ 历史原文召回
+ Fragment / Episode / Saga
+ Lore
+ 知识库
+ 消息封装与安全余量
+ 预留输出 token
<= 当前 Provider + Model 的上下文窗口
```

若不满足，则按以下顺序缩减：

1. 减少低相关知识片段。
2. 减少低相关历史原文召回。
3. 减少低相关 Episode/Saga。
4. 减少低相关 Fragment，但保留明确相关和受保护长期事实。
5. 减少更早的最近原文轮次，并由摘要承接。
6. 压缩 Lore 的非核心部分。
7. 若受保护区仍无法放入，调用前失败并提示用户缩短输入或切换更大上下文模型。

不得通过裁剪当前用户消息、安全规则或输出预留来“凑够”预算。

### 5.2 模型能力来源

模型窗口必须按 `provider_id + model_id` 解析，优先级为：

1. 已验证的 ModelProfile 能力值。
2. Provider 能力发现或官方适配器的模型映射。
3. 用户显式配置的保守值。
4. 未知模型使用保守默认值并标记 `unverified`。

不再在 `context_budget.py` 中维护一份仅按 Provider 名称判断的长期硬编码表。

### 5.3 token 估算策略

- 第一版允许使用本地保守估算，但只能有一个权威实现。
- 估算接口必须能区分消息正文、角色封装、工具协议和附件描述。
- 可用时由适配器提供更精确 tokenizer；不可用时使用保守系数并增加 safety margin。
- 每次请求都记录估算版本、总量和各组件数量，不记录正文。
- Provider 返回真实 usage 时，记录估算误差，用于离线校准，不自动放宽安全边界。

## 6. 会话滚动摘要设计

### 6.1 摘要应该保留的内容

- 当前会话的主题和目标。
- 用户已经明确作出的决定。
- 用户对旧内容的纠正。
- 已完成、正在进行和未解决的事项。
- 后文仍会引用的人物、文件、项目和术语。
- 遐蝶已经作出的承诺或需要继续履行的动作。
- 必要的情绪与关系语境，但不得把瞬时情绪固化为永久事实。

### 6.2 摘要不应保留的内容

- 可从长期记忆直接获取且与会话连续性无关的重复事实。
- 无后续意义的寒暄和一次性计算细节。
- 密码、API Key、令牌、身份证号等秘密。
- 模型内部推理。
- 没有原文支持的推断。
- 知识库正文的大段复制。

### 6.3 建议数据模型

```text
conversation_summary_revisions
├─ id
├─ session_id
├─ revision
├─ status
├─ protocol_version
├─ source_start_message_id
├─ source_end_message_id
├─ source_message_count
├─ source_sha256
├─ summary_text
├─ open_threads_json
├─ decisions_json
├─ corrections_json
├─ entity_refs_json
├─ provider_id
├─ model
├─ prompt_tokens
├─ completion_tokens
├─ error_code
├─ created_at
├─ activated_at
└─ superseded_at

conversation_summary_runs
├─ id
├─ session_id
├─ target_end_message_id
├─ source_sha256
├─ status
├─ attempts
├─ next_attempt_at
├─ lease / heartbeat
├─ error_code
├─ created_at
└─ updated_at

conversation_summary_events
└─ 只保存 ID、状态、版本、数量、耗时和错误码，不保存正文
```

### 6.4 版本与失效

- 同一会话任一时刻只有一个 active 摘要版本。
- 新摘要原子激活后，旧摘要变为 superseded。
- 摘要覆盖的来源范围必须连续，不能跳过中间消息。
- 重新生成替换消息后，覆盖旧 assistant message 的摘要必须失效。
- 删除会话时通过外键级联删除摘要和任务。
- 应用崩溃后可恢复 queued/running 任务，但不能重复激活相同来源哈希。
- 增量摘要允许使用“旧 active 摘要 + 新增原文”，但必须定期从原始消息全量重建以控制摘要漂移。

### 6.5 触发策略

触发不应只看“轮数”，而应同时考虑：

- 当前模型的可用输入预算。
- 未摘要历史的估算 token。
- 最近原文保护窗口。
- 上次 active 摘要覆盖位置。
- 当前是否已有同来源任务。

建议行为：

1. 低于软阈值：不生成摘要，直接保留原文。
2. 接近软阈值：后台生成或更新摘要。
3. 摘要尚未完成但用户继续聊天：安全裁剪旧原文，当前请求不中断。
4. 达到硬阈值：只使用已验证摘要和可容纳的最近完整轮次。
5. 连受保护区都无法容纳：调用前明确失败。

## 7. 历史对话召回设计

### 7.1 为什么摘要还不够

摘要是有损的。用户可能问：

- “我以前是不是问过你 12×8？”
- “我当时对 UI 的原话是什么？”
- “我们第一次提到 Blender 是哪次？”

这些问题必须回到原始消息，而不是依赖摘要。

### 7.2 第一版召回范围

1. 优先检索当前会话中已被摘要覆盖的旧消息。
2. 用户明确要求回忆过去时，允许检索其他会话。
3. 使用本地 SQLite FTS，不默认把全部历史发送给远程模型。
4. 返回成对或完整轮次，避免只取一条 assistant 回复而丢失问题。
5. 每个召回片段携带 session、message、时间和相邻上下文引用。
6. 普通闲聊不默认搜索所有旧会话；跨会话召回应可配置并有明确触发器。

### 7.3 与 Episode 的区别

```text
历史对话召回：回答“具体说过什么、什么时候说的”，证据是原始消息。
Episode：回答“我们共同经历了什么”，证据是经过整理的记忆来源链。
```

两者都可以进入 ContextPackage，但必须使用不同标签，模型不得把 Episode 摘要冒充用户原话。

- [ ] 不允许同一旧消息既以完整原文又以摘要重复占用预算，除非它被按需历史召回。

- [ ] 长知识片段、长记忆、长 Lore 与长用户输入同时出现。

## 9. 必测场景矩阵

| 场景 | 预期结果 |
|---|---|
| 短会话 | 不必生成摘要，保留完整最近原文 |
| 长会话，摘要可用 | 注入 active 摘要 + 摘要后的最近完整轮次 |
| 长会话，摘要失败 | 安全裁剪，聊天继续，meta 标明摘要不可用 |
| 系统提示过长 | Provider 调用前失败，不伪造可用预算 |
| 当前用户输入过长 | 明确提示缩短输入或更换模型 |
| 切换小上下文模型 | 重新编排，不沿用大模型预算 |
| 切换远程 Provider | 不意外发送旧历史做摘要 |
| 重新生成最后回复 | 旧回复成功替换后使相关摘要失效/重建 |
| 删除会话 | 原文、摘要、索引按策略级联清理 |
| “我问过 12×8 吗” | 历史召回原消息，不新建长期 Fragment |
| “我喜欢什么窗口” | 优先召回相关长期偏好，可辅以原对话证据 |
| 关闭已保存记忆 | 不读取或新增长期记忆，但同一聊天仍能延续 |
| 关闭参考聊天历史 | 新聊天不检索旧会话，但显式保存的长期记忆仍可使用 |
| 临时聊天 | 只使用本次临时会话上下文，不读写个人记忆与跨会话历史 |
| 删除聊天但保留记忆 | 旧聊天不再被历史召回，独立长期记忆按提示保留 |
| 删除聊天及派生记忆 | 显示影响范围并清理双方关联数据，留下无正文审计 |
| 摘要与原文冲突 | 原文和用户最新纠正优先，摘要失效 |
| 知识库内容很长 | 知识先按独立预算缩减，不挤掉当前问题 |
| Provider 返回 context error | 记录结构化错误；仅在无副作用前提下允许一次保守重编排 |

## 10. 审查规则

1. 每个 CTX 阶段使用独立分支或最小 PR，不跨阶段“顺手实现”。
2. 每阶段完成后生成专属审查材料；下一阶段开始前只读取一次新审查反馈。
3. 审查报告若基于过时测试数、过时 schema 或旧源码，必须先校准基线再决定是否采纳。
4. 审查建议分为：采纳、调整后采纳、推迟、拒绝；每项写清理由和落点。
5. 未完成的测试、UI、迁移或隐私项不能因“主流程可用”而提前打勾。
6. 阶段提交不得包含用户已有的无关工作区改动。
7. 所有新增事件表都要验证不保存正文、摘要正文和模型原始输出。
8. 所有模型生成摘要都必须经过本地 Schema、来源和敏感信息校验。
9. 所有预算结论必须由测试证明，不接受“通常不会超过”的经验判断。
10. 总验收之前不得删除临时兼容接口；总验收后应清除重复 estimator、失效常量和旧拼接路径。

## 13. 最终产品体验

完成本计划后，用户应感受到：

1. 同一会话聊很久，遐蝶仍能延续早期决定和未完成话题。
2. 她不会因为上下文变长突然报错，也不会无提示忘掉前文。
3. 她记得稳定偏好，是长期记忆在工作。
4. 她能找回“以前具体说过什么”，是历史对话召回在工作。
5. 她对长会话的连续理解，是滚动摘要与最近原文共同工作。
6. 用户始终可以打开原会话验证，而不必相信一段不可追溯的摘要。
7. 用户可以像使用 ChatGPT 一样分别控制“记住我的信息”和“参考过去聊天”。
8. 临时聊天不会在之后的聊天里突然被提起。
