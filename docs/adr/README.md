# 架构决策记录（ADR）

ADR 用来保存“为什么这样设计”，避免几个月后只看到代码结果却不知道当时的约束。

## 什么时候需要 ADR

以下决策应创建 ADR：

- 更换或新增核心框架、数据库、模型协议或进程边界；
- 改变本地数据位置、schema、迁移或加密方式；
- 改变工具权限分级、确认机制或外部副作用规则；
- 引入浏览器控制、桌面自动化、外部平台或多 Agent；
- 做出难以回退、会影响多个后续版本的技术选择。

普通 bug 修复、样式微调、局部重构和已由路线图明确规定的实现细节通常不需要 ADR。

## 文件规则

- 文件名：`NNNN-short-title.md`，例如 `0001-local-api-boundary.md`。
- 编号按目录中最大编号递增，不复用已废弃编号。
- 从 [ADR_TEMPLATE.md](ADR_TEMPLATE.md) 复制创建。
- 一份 ADR 只记录一个主要决策。

## 状态

- `Proposed`：正在讨论，尚未作为实现依据。
- `Accepted`：已接受，当前实现应遵循。
- `Superseded`：被新的 ADR 取代，保留历史。
- `Rejected`：评估后未采用，保留原因。

不要直接重写已接受 ADR 的核心结论。决策改变时创建新 ADR，并在新旧文档中互相链接。
