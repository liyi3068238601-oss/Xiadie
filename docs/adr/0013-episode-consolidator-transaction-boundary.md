# ADR-0013：Episode Consolidator 的任务、事务与幂等边界

- 状态：Accepted
- 日期：2026-07-15
- 决策者：项目所有者、Codex
- 关联版本/任务：记忆系统阶段 C
- 取代：无
- 被取代：评分权重顺序由 ADR-0014 部分取代；其余事务与恢复决策仍有效

## 背景

现有 `episodes.py` 是人工确认原型：写入 Fragment 时同步寻找关联片段、生成 pending 候选，
再由用户接受后创建正式 Episode。最终形态需要后台自动整理，但不能把模型调用或长时间分组
放进聊天及 Fragment 写入事务，也不能因为重试、崩溃或两个 worker 并发而重复创建 Episode。

必须保持的边界：

- Fragment 是事实来源；整理失败不能修改或删除 Fragment。
- 每个正式 Fragment 最多属于一个正式 Episode。
- Episode 必须保留有序 Fragment、实体、时间范围和可审计来源。
- 旧候选表和确认 API 在自动流程稳定前继续兼容，不能冒充自主合成结果。
- 后台任务必须可排队、可取消、可恢复，并且状态转换可审计。

## 决策

### 1. 两层事务

Consolidator 使用两个短事务，不持有跨模型调用的数据库事务：

1. **任务事务**：原子认领一个 due run，记录 `running`、租约/更新时间和尝试次数，然后提交。
2. **应用事务**：模型结果通过协议与来源事实校验后，重新读取并锁定来源边界；在同一事务内写入
   Episode、按顺序写入 Fragment 关联、继承实体、记录来源集合与审计事件，最后将 run 标记为
   `applied`。

模型调用、摘要生成和事实校验位于两层事务之间。任何异常只改变 run 状态，不改变 Fragment。

### 2. 任务状态机

```text
queued ──认领──> running ──校验并提交──> applied
  │                 │  │
  │                 │  ├──可重试失败──> recovery_pending ──到期──> running
  │                 │  ├──耗尽/不可恢复──> exhausted
  │                 │  └──取消请求──> cancel_requested ──安全点──> cancelled
  └──取消──> cancelled

recovery_pending ──取消──> cancelled
queued/running/recovery_pending ──没有合格分组──> skipped
```

- `applied`、`cancelled`、`exhausted`、`skipped` 是终态。
- queued/recovery_pending 可立即取消；running 只写 `cancel_requested`，worker 在模型调用前后和
  应用事务开始前检查。正式 Episode 一旦提交，不再用“取消”反向删除。
- worker 崩溃后，超过租约的 running 转为 recovery_pending；重试不复用不完整数据库写入。
- 每次状态变化写入独立事件表，保存前后状态、原因码与不含正文的结构化元数据。

### 3. 分组与重复边界

> 本节的评分权重顺序已由 ADR-0014 纠正并取代；实现必须以 ADR-0014 和设计书第 12 节为准。

- 输入只选 active、enabled、尚未属于正式 Episode 的 Fragment。
- 一组必须有 2～20 条、跨度不超过 7 天，并满足共同实体边界。
- 分组分数为：时间接近度 0.35、共同实体 0.25、主题相似度 0.20、关系重要度 0.20；低于
  0.50 不得自动提交。
- `grouping_fingerprint = SHA-256(policy_version + 排序后的 fragment_id)`。它不包含标题或摘要，
  避免模型措辞变化绕过幂等。
- 正式 Episode 保存该指纹并建立唯一约束；应用事务还必须重新检查每个 Fragment 的唯一归属。
- 同一批来源出现不同重叠分组时，按分数、来源数量、最早时间、指纹稳定排序，只允许第一个
  成功占用；其余分组重新计算。

### 4. 低分候选与失败恢复

- 低于 0.50 的分组只保存来源 ID、各评分分量和到期时间，不保存模型虚构摘要。
- 候选最多保留 7 天；新 Fragment 到来可重新评估。到期只清候选，不删除 Fragment。
- 可重试错误采用有限退避，最多 3 次；协议错误可进行一次受限 JSON 修复，仍失败则 exhausted。
- Episode 摘要必须能逐项追溯到来源 Fragment；事实校验失败不得降阈值强行提交。

### 5. 调度边界

- 聊天/Fragment 写入热路径最多发出幂等 enqueue，不执行分组或模型调用。
- 应用启动时恢复陈旧任务；空闲信号触发检查。后台 worker 使用事件唤醒和有界超时，不用阻塞
  聊天的定时循环。
- 单次批量、模型 token、耗时与重试次数必须有上限；具体预算在 C.2/C.3 实现时固化。

## 备选方案

### 继续同步候选并要求用户确认

- 优点：实现简单，用户可直接纠错。
- 缺点：不符合角色自主记忆定位；聊天写入事务承担整理工作；无法可靠恢复后台失败。
- 未采用原因：只能作为迁移兼容，不是最终形态。

### 一个长事务包住分组、模型调用和写入

- 优点：表面上容易理解“全部成功或失败”。
- 缺点：长时间占用 SQLite 写锁，崩溃恢复困难，取消与并发行为不可控。
- 未采用原因：会阻塞本地应用的聊天与记忆写入。

### 只依赖摘要文本去重

- 优点：无需额外来源指纹。
- 缺点：模型措辞不稳定，同一来源可以生成不同摘要并产生重复 Episode。
- 未采用原因：来源集合才是稳定的幂等边界。

## 后果

### 正面后果

- 后台失败与聊天、Fragment 写入隔离。
- 每个任务状态和失败原因可追踪，崩溃后能安全恢复。
- 来源指纹与唯一归属共同防止重复 Episode。
- 用户无需逐条确认，同时仍可在正式 Episode 上查看来源和纠错。

### 代价与限制

- 需要新增任务/事件表、低分候选存储和后台 worker。
- 自动合成会有延迟，不能保证 Fragment 写入后立刻看到 Episode。
- 取消是协作式取消，不能撤销已经原子提交的正式 Episode。

## 安全与隐私

- 权限等级：本地 S0；不触发工具或外部副作用。
- 涉及的数据：Fragment 内容、实体关系、来源消息 ID、模型摘要。
- 是否访问网络：仅在用户已配置的模型供应商上生成摘要；任务账本本身不访问网络。
- 是否产生外部副作用：否。
- 用户确认和审计方式：不要求逐条确认；展示来源、评分与任务事件，保留人工纠错/删除能力。

任务事件不得保存 Fragment 正文、模型密钥或完整 prompt；只保存 ID、计数、评分和错误码。

## 数据与迁移

- C.1 新增 `episode_consolidator_runs` 与 `episode_consolidator_events`。
- 后续新增低分分组表，并给正式 Episode 增加 `grouping_fingerprint`、策略版本和来源集合字段。
- 旧 `memory_episode_candidates`、确认 API 与数据继续可读，直至独立退役阶段满足迁移条件。
- 失败恢复通过任务状态和有限租约完成；正式应用写入必须使用单个 SQLite 事务。

## 验证

- 自动测试：迁移、幂等 enqueue、合法/非法状态转换、queued/running 取消语义、事件顺序。
- 后续自动测试：阈值边界、重叠分组、来源继承、重复运行、应用回滚、陈旧任务恢复。
- 手工验收：不使用内置浏览器；待界面阶段通过构建与自动化组件测试验证。
- 监控或日志：run 保存状态、尝试次数、错误码、计数、耗时；事件保存每次转换。

## 回滚

停止 Consolidator worker 和新 enqueue 即可回到旧候选流程。新增表可留存而不被旧代码读取；不要
在同一次回滚中删除表。已经生成的正式 Episode 仍作为普通 Episode 保留，不自动拆散或删除来源。
