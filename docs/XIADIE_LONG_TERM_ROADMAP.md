# 遐蝶桌面 Agent 长期开发路线

> 文档状态：当前长期执行依据  
> 起点版本：v0.1.0  
> 目标形态：安全、可控、可扩展的本地优先桌面伴侣 Agent  
> 更新规则：每完成一个小版本，必须同步更新本文件中的状态、验收结果和下一阶段入口。

## 0. 这份文档解决什么问题

本文件把遐蝶从当前可运行的桌面聊天伴侣，逐步推进到完整桌面 Agent 的过程固定下来。

后续开发必须遵循以下节奏：

1. 每次只完成一个边界清楚、可以独立验收的主题。
2. 先让底层安全、可靠、可测试，再增加工具和自动化能力。
3. 先做单主控 Agent Core，再逐步拆出 Worker Agent。
4. 先做只读能力，再做可写能力；先做本地能力，再做外部影响能力。
5. 高风险操作始终需要明确授权、审计记录、取消机制和回滚方案。
6. 不为了追赶路线图而跳过测试、权限、日志、迁移和失败恢复。

设计稿版本号与应用版本号是两套概念。旧设计文档中的 v0.3、v0.5、v0.6 是文档修订号；本路线中的 v0.1.1、v0.2.0、v1.0.0 是实际应用版本。

## 1. 产品定位与最终完成定义

### 1.1 一句话定位

遐蝶是一个常驻 Windows 桌面的 AI 伴侣 Agent：她能理解用户意图、记住重要信息、规划任务、调用受控工具、处理本地资料、生成可追溯产物，并在有风险的动作前请求确认。

### 1.2 最终用户体验

```text
启动遐蝶
  ↓
桌面只显示固定角色的 Live2D 桌宠
  ↓
用户点击桌宠或使用托盘/快捷键
  ↓
打开单一遐蝶主窗口
  ↓
用户可以聊天、交付资料、创建任务或要求执行工作
  ↓
Agent 分析目标并形成可见计划
  ↓
按权限调用文件、知识、浏览器、办公和外部连接工具
  ↓
高风险步骤弹出确认卡，用户可以允许、拒绝、修改或停止
  ↓
执行过程持续显示进度、日志、下一动作和输出产物
  ↓
Verifier 检查结果，失败时安全重试或请求用户介入
  ↓
结果、来源、产物、记忆和审计记录均可查看、导出和删除
```

### 1.3 最终 Agent 必须具备的能力

- 陪伴式多轮聊天和稳定角色表达。
- 多模型 Provider 配置、能力识别和可解释路由。
- 可控的短期上下文、长期记忆和用户画像。
- 本地文件读取、编辑、生成和产物管理。
- PDF、Word、Excel、Markdown、文本和图片资料处理。
- 可追溯知识库、语义检索和回答引用。
- 任务规划、步骤执行、暂停、继续、取消、重试和重新规划。
- 搜索、浏览器、办公、网络 API 和外部消息等工具能力。
- 分级权限、逐次确认、最小授权、急停和审计。
- 单主控与多个专业 Worker 的渐进式协作。
- 故障诊断、结果验证、幂等处理和安全恢复。
- 数据导出、备份、恢复、迁移和隐私删除。
- Windows 安装、升级、日志收集和稳定发布。

### 1.4 最终 Agent 明确不能做的事

- 不得绕过用户确认执行高风险动作。
- 不得静默发送消息、付款、下单、删除数据或修改生产系统。
- 不得在用户不知情时扫描硬盘、上传文件或保存敏感记忆。
- 不得把网页、文件或外部工具返回的内容当作更高优先级系统指令。
- 不得自行扩大目录、账号、应用或网络权限。
- 不得静默修改自身代码、自动部署或自动覆盖稳定版本。
- 不得使用授权不清楚的 Live2D、角色、美术、音频或模型资源对外发布。
- 不得为了“全能”而一次性开放 Shell、输入控制和任意网络访问。

## 2. 权威技术与产品决策

### 2.1 冻结的技术路线

| 层级 | 当前及长期选择 | 原则 |
| --- | --- | --- |
| 桌面壳 | Electron | 保留现有实现，不迁移 Tauri。 |
| 前端 | React + TypeScript + Vite | 逐步拆分，不推倒重写。 |
| 后端 | Python + FastAPI | 继续作为 Agent Core 和工具执行底座。 |
| 本地存储 | SQLite | 先保持单机可靠，迁移必须可回滚。 |
| 模型协议 | OpenAI-compatible 为基础 | 通过适配层支持差异，不把供应商逻辑散落到业务层。 |
| 桌宠 | 固定内置 Live2D | 不提供用户导入、替换、市场或路径选择。 |
| UI 结构 | 桌宠入口 + 单主窗口 + 按需面板 | 不走默认多窗口路线。 |
| Agent 形态 | 单主控优先，Worker 渐进拆分 | 先验证工具协议，再引入真实多 Agent。 |

### 2.2 文档参考优先级

如旧文档之间存在冲突，按以下顺序处理：

1. 本文件及仓库内后续 ADR。
2. `遐蝶Agent_v0.2UI回归与Cyrene风格融合迁移方案_v0.6.1`。
3. `遐蝶桌面Agent_UI设计规格书_Cyrene融合回归版_v0.3.1`。
4. `遐蝶桌面Agent_Cyrene路线版总体设计与开发计划_v0.5.1`。
5. `遐蝶Agent_Codex_PR拆分执行计划_v0.6.2`。
6. 旧版 UI、多 Agent、长期路线文档只作细节和远期架构参考。

以下旧路线已明确失效：Tauri、多窗口优先、用户导入 Live2D、早期 QQ、早期桌面自动化、立即拆分多 Agent。

## 3. 当前 v0.1.0 基线

### 3.1 已经实现

- Electron 桌宠、托盘、右键菜单、主窗口和状态联动。
- 固定路径 Live2D 加载与模型缺失占位。
- React 三栏主窗口和紫蓝玻璃拟态基础视觉。
- 会话创建、删除、自动标题和消息历史。
- SSE 流式聊天、复制、收藏、重试和重新生成。
- 多个 OpenAI-compatible Provider 的配置、测试和切换。
- Mock 演示模型。
- L0/L1/L2 记忆的增删改查、启用和基础注入。
- 任务创建、状态流转、删除和从对话创建任务。
- 文件与知识、工具记录、权限和数据设置的页面骨架。
- SQLite 本地存储。
- Windows 构建脚本和双击开发启动脚本。
- 后端 11 项测试、前端生产构建和 Electron 脚本检查。

### 3.2 已实现但仍不完整

- Provider 能力标签目前主要通过模型名称猜测，不是可靠能力模型。
- 自动记忆目前是关键词启发式，不具备敏感信息识别和确认流程。
- “今日任务”只是取未完成任务，不是真正的日期调度。
- 工具记录只有表结构和读取页面，没有真实 ToolRegistry 和审计写入。
- 权限页面只有说明，没有后端策略执行和确认闭环。
- Live2D 设置多数是占位，没有真实持久化和 IPC 行为。
- 当前本地 Live2D 素材仅允许个人自用，不能进入公开仓库或正式发行包。

### 3.3 当前关键风险

- 本地 FastAPI 允许任意来源访问，缺少桌面端访问令牌。
- API Key 仍明文存放在 SQLite。
- 重新生成会先删除旧回复，新请求失败时可能丢失内容。
- 聊天历史没有上下文预算和摘要机制。
- 模型选择缺少严格校验。
- 前端缺少系统性的组件测试和 Electron 端到端测试。
- 应用版本、数据库迁移和发布流程尚未形成正式规范。

## 4. 每个小任务的统一执行规范

### 4.1 任务大小

- 每次只做一个主题。
- 通常修改不超过 8 至 12 个文件。
- 超过 15 个文件时必须先停止，说明为什么不能继续拆分。
- 不在同一个任务中混合大重构、新功能和视觉改版。
- 不做未在任务范围内的“顺手优化”。

### 4.2 每次开始前

1. 阅读本文件对应阶段。
2. 检查 `git status`，保护用户已有修改。
3. 写清本轮目标、不做事项、风险和验证命令。
4. 确认是否涉及数据库迁移、权限扩大、外部写入或发布行为。
5. 如果行为会改变用户数据，先定义回滚和备份方式。

### 4.3 每次完成后

- 后端修改：运行全部后端测试。
- 前端修改：运行 TypeScript 检查和生产构建。
- Electron 修改：运行语法检查，并按风险进行桌面启动验证。
- 数据库修改：测试新库初始化、旧库迁移、迁移重复执行和失败回滚。
- 权限修改：测试允许、拒绝、超时、取消和越权五种情况。
- 文件修改：测试路径逃逸、大小限制、编码、并发修改和失败恢复。
- 输出修改文件、行为变化、验证结果、已知风险和下一步。
- 形成单一目的提交并推送；阶段完成后再打版本标签。

### 4.4 通用完成标准

一个任务只有同时满足以下条件才算完成：

- 正常路径可用。
- 失败路径有清晰提示。
- 用户取消不会留下半完成状态。
- 日志不泄露密钥、文件正文或敏感参数。
- 无静默权限扩大。
- 测试和构建通过。
- 文档与真实行为一致。

## 6. v0.1.1：治理与本地安全

目标：不新增“酷功能”，先解决继续扩展会放大的安全问题。

### 6.1 文档治理

1. 创建 `docs/CODEX_PROJECT_CONTEXT.md`，记录不可变决策和禁止事项。
2. 创建 `docs/BASELINE_STATUS.md`，记录当前启动、测试、构建和功能状态。
3. 创建 `docs/PR_CHECKLIST.md`，固定每轮范围和验收模板。
4. 创建 `docs/adr/`，为重要技术决策保留 ADR。
5. 在 README 中链接本路线和当前状态文档。

### 6.2 本地 API 访问保护

1. Electron 每次启动生成高强度随机本地令牌。
2. 令牌通过受控 preload 桥接交给主窗口，不进入 URL、日志和 localStorage。
3. 前端所有 API 请求携带令牌。
4. 后端中间件校验令牌，健康检查只暴露最少信息。
5. CORS 从 `*` 改为明确允许的本地开发源和 Electron 来源策略。
6. 测试无令牌、错误令牌、正确令牌和开发模式。
7. 打包模式下验证令牌传递和后端重启。

### 6.3 Provider 与密钥边界

1. 抽象 SecretStore 接口，不让业务代码直接依赖 SQLite 密钥字段。
2. 开发模式可保留受限兼容层，正式模式使用 Electron `safeStorage`。
3. 明确新增、更新、清除和检测密钥的行为。
4. API 永不返回完整密钥，只返回 `has_key` 和必要状态。
5. 日志、异常和连接测试结果统一脱敏。
6. 设计旧 SQLite 密钥迁移流程：读取、写入安全存储、验证、清除旧值。

### 6.4 本版本验收

- 任意普通网页不能读取或修改本机遐蝶数据。
- Electron 主窗口仍可正常使用所有现有接口。
- API Key 不出现在响应、日志和错误信息中。
- 旧用户数据可继续使用。
- 后端测试、前端构建和桌面启动全部通过。

## 7. v0.1.2：聊天、上下文和数据可靠性

### 7.1 重新生成安全化

1. 生成新回复前不删除旧回复。
2. 新回复完整落库后，再以事务替换旧回复或建立版本关系。
3. 生成失败、取消或断网时保留旧内容。
4. 前端允许查看回复版本并恢复上一版。

### 7.2 上下文预算

1. 为每个 Provider/Model 定义上下文能力。
2. 计算系统提示、记忆、历史和当前输入的预算。
3. 优先保留系统规则、最近对话和明确相关记忆。
4. 长会话生成可查看的阶段摘要。
5. 摘要不得覆盖原始消息，只作为派生数据。
6. 模型超限前主动裁剪并向用户提供可诊断信息。

### 7.3 输入与数据校验

1. 限制消息、标题、任务和记忆的长度。
2. 严格校验 Provider 是否存在、是否启用、模型是否属于可用列表。
3. 删除不存在资源时返回明确状态，不伪装成功。
4. 统一 API 错误结构和前端错误卡。
5. 为 SQLite 增加必要索引、事务边界和备份测试。

### 7.4 本版本验收

- 长会话不会无限发送全部历史。
- 重新生成失败不会丢失旧回复。
- 非法模型、空值、超长输入和损坏设置都有明确结果。
- 数据库异常不会让聊天永久失效。

## 9. v0.2.0：ToolRegistry 与权限内核

这是从“聊天应用”变成“Agent”的第一个关键版本。

### 9.1 工具定义

建立统一对象：

```text
ToolDefinition
├─ name / version / description
├─ input_schema / output_schema
├─ risk_level
├─ required_capabilities
├─ timeout / retry_policy
├─ idempotent
├─ preview()
└─ execute()
```

### 9.2 注册表

1. 工具显式注册，不允许按字符串动态导入任意代码。
2. 启动时检查工具名、版本、Schema 和权限声明。
3. 提供列出工具、查询工具和执行工具的内部接口。
4. 第一阶段不接模型 function calling，只用测试和本地命令验证。

### 9.3 权限内核

建议风险等级：

| 等级 | 示例 | 默认策略 |
| --- | --- | --- |
| S0 | 展示、计算、格式转换 | 自动允许并记录。 |
| S1 | 读取用户明确选择的本地范围 | 在已授权范围内允许。 |
| S2 | 修改本地数据或文件 | 每次预览并确认。 |
| S3 | 外发消息、网络写入、操作应用 | 强确认，展示目标和参数。 |
| S4 | Shell、输入控制、系统设置、付款 | 默认禁用，后期白名单开放。 |

权限决策至少包含：工具、风险、资源范围、会话、有效期、参数摘要和用户决定。

### 9.4 审计事件

每次工具调用记录：

- 调用 ID、任务 ID、会话 ID。
- 工具名和版本。

## 14. v0.4.1：可靠记忆系统

## 16. v0.5.1：Planner / Executor / Verifier

### 16.1 Planner

- 把用户目标转换为有限、有依赖关系的步骤。
- 每一步声明输入、输出、工具、风险和完成条件。
- 缺少关键参数时先询问，不凭空决定。
- 计划长度、重规划次数和成本有上限。

### 16.2 Executor

- 只执行已经批准且依赖满足的步骤。
- 每次只获取最小必要能力令牌。
- 执行前再次检查资源范围和参数。
- 记录开始、心跳、结果、产物和错误。

### 16.3 Verifier

- 根据步骤完成条件检查结果，不只相信模型自述。
- 文件结果检查存在性、格式、大小和必要内容。
- 结构化结果检查 Schema。
- 外部动作检查可确认的回执。
- 无法验证时标记“需要人工确认”，不能伪装成功。

### 16.4 本版本验收

- 一个包含读取、处理、生成和保存的多步骤本地任务可完整执行。
- 任一步失败时不会越过失败步骤继续产生外部影响。
- 重规划不会绕过原权限决定。
- 完成状态必须有验证证据。

## 21. v0.9.0：多 Agent Worker 化

### 21.1 何时才允许拆 Worker

同时满足以下条件后才开始：

- ToolRegistry 已稳定。
- TaskRun/TaskNode 状态机已稳定。

- 单主控能可靠完成目标场景。
- 已有明确性能、隔离或专业上下文需求，证明拆 Worker 有价值。

### 21.2 推荐拓扑

```text
CompanionAgent
  ↓
Orchestrator
  ├─ KnowledgeAgent
  ├─ FileDataAgent
  ├─ BrowserAgent
  ├─ OfficeAgent
  ├─ MemoryAgent
  └─ VerifierAgent
       ↓
ToolRegistry + PolicyGuard + Scheduler + Audit
```

### 21.3 第一批 Worker

1. KnowledgeAgent：检索、引用和知识范围控制。
2. FileDataAgent：文档读取、数据转换和产物生成。
3. VerifierAgent：独立检查结果和完成条件。

MemoryAgent、BrowserAgent、MessageAgent 和 DesktopExecutorAgent 后续按需求增加。

### 21.4 协作协议

- Worker 不直接与用户争夺最终回答权。
- Worker 不拥有永久权限，只获得任务节点级能力令牌。
- 通过结构化事件和产物通信，不依赖隐式聊天上下文。
- Scheduler 控制并发、超时、资源租约和取消。
- Orchestrator 不能自行批准高风险动作。

### 21.5 本版本验收

- Worker 失败不会拖垮整个桌面应用。
- 同一文件、浏览器会话或外部资源不会被冲突操作。
- 用户看到的是统一任务过程，而不是多个 Agent 混乱对话。
- 多 Agent 相比单主控在目标场景中有可测量收益。

### 24.1 语音与多模态

- TTS 先于 ASR。
- 语音开关、音量、隐私和数据流向明确。
- 图片理解、截图问答和视觉任务接入统一工具协议。
- 语音不能绕过文字确认卡和权限策略。

### 24.2 插件体系

- 插件有 Manifest、版本、签名、能力声明和权限清单。
- 插件运行在隔离边界，不能直接访问全部数据库和文件系统。
- 安装、升级、禁用和卸载可回滚。
- 插件市场只有在审核、签名和权限 UI 完成后考虑。

### 24.3 有边界的自我修复

允许：收集错误、定位问题、生成修复建议、生成补丁、运行隔离测试、展示 diff 和回滚方案。

禁止：静默修改稳定版本、自动提交、自动推送、自动部署或绕过人工审批。

### 24.4 专项能力

Blender、DCC、游戏、复杂办公自动化等能力以独立插件或 Worker 提供，不进入核心内核，也不得降低核心安全策略。

## 25. v2.0.0：成熟个人 Agent 平台

v2.0 不是“无限权限的全能 AI”，而是可组合、可解释、可恢复、由用户持续掌控的个人 Agent 平台。

最终架构应具备：

- 稳定 CompanionAgent 作为唯一用户入口。
- Orchestrator 根据任务选择专业 Worker。
- Scheduler 管理并发、资源、成本和取消。
- PolicyGuard 在所有执行路径上统一生效。
- ToolRegistry 和 ConnectorRegistry 提供可审计能力。
- Memory 与 Knowledge 分离，来源、生命周期和权限明确。
- ArtifactStore 管理所有输出和版本。
- Verifier 对关键结果进行独立检查。
- Eval 系统持续衡量质量、可靠性和安全性。
- 插件和 Worker 可以扩展，但不能绕过核心治理。

v2.0 的最终成功标准：普通用户能够把一个真实、复杂、跨资料和工具的目标交给遐蝶；用户始终能看见她准备做什么、正在做什么、为什么需要权限、产生了什么结果，并能随时暂停、拒绝、回滚和删除。

## 26. 版本推进和暂停规则

### 26.1 可以进入下一阶段的条件

- 当前版本所有必须验收项通过。
- 没有未处理的高危安全问题。
- 数据迁移和回滚已经验证。
- 文档与代码一致。
- 工作区干净，提交已推送并打阶段标签。

### 26.2 必须暂停扩展的情况

- 出现数据丢失、权限绕过或密钥泄露。
- 测试持续不稳定，无法判断失败原因。
- 为实现新功能需要一次性修改过多模块。
- 旧数据迁移路径不明确。
- 外部平台授权或素材许可不清楚。
- 当前基础能力尚未被真实使用场景验证。

### 26.3 允许调整路线的方式

1. 先记录现状和调整原因。
2. 创建 ADR，列出方案、替代项、影响和回滚条件。
3. 只修改受影响阶段，不静默重写全部路线。
4. 保留已完成版本和历史决策。
